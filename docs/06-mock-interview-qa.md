### 0.4 项目 2 分钟版

“我的项目目标是辅助历史 Fortran 数值代码迁移到 C++。这个任务的难点不是简单生成 C++，而是 Fortran 和 C++ 在数组索引、列主序、浮点精度、过程参数、I/O 和全局状态上存在大量语义差异，模型很容易生成‘看起来对但编译不过或结果不对’的代码。

所以我把项目拆成三层。第一层是模型：在 Qwen2.5-Coder-7B 上做领域 LoRA，让模型稳定输出结构化结果和较一致的 C++17 风格。第二层是数据：用公开的宽松许可 Fortran 代码和强模型合成平行数据，每条样本必须经过 gfortran 和 g++ 双端编译、运行和输出对比，不能只靠模型自评。第三层是 Agent：用 LangGraph 把翻译、编译、运行、数值对比、错误诊断和修复做成状态机，并放在 Docker 沙箱里执行，加上最大迭代、震荡检测和资源限制。

硬件上，本地是 Intel NUC，没有 CUDA，只做 2B 模型 CPU 冒烟、数据处理和 Agent 开发；正式训练在 2×A800 40GB 上，PyTorch 2.1、CUDA 12.1、Python 3.10。考虑到单卡 40GB 和短周期目标，MVP 选择 7B bf16 LoRA，而不是 14B/30B。最终部署会把 adapter 合并成 GGUF，量化到 Q4_K_M，用 Ollama 加载。

评测上我会比较 base few-shot、LoRA 和 LoRA+Agent，关注 JSON 有效率、编译成功率、测试通过率、数值等价率、平均迭代数和修复成功率。当前第一个真实基线已经暴露了问题：本地 2B 模型能返回合法 JSON，但生成的代码缺少头文件，也没有保留格式宽度，这正好说明为什么必须有编译和测试闭环。”

## 1. 项目与动机高频问题

### Q1：为什么做 Fortran→C++，而不是其他语言？

**参考回答：**

选择 Fortran→C++ 有三个原因。第一，现实需求明确：科学计算和工业遗留系统里仍有大量 Fortran 代码，迁移到 C++ 可以接入现代工程生态。第二，任务边界相对清晰：输入输出、编译器和测试都能自动化验证，适合做“模型+工具”的闭环。第三，技术挑战有代表性：数组列主序、1-based 索引、浮点语义、过程参数和 I/O 差异，能体现代码翻译不是普通文本生成。

**追问：为什么不做 Python？**  
Python 适合快速原型，但 C++ 更贴近工业迁移场景，也更能体现接口、内存和数值语义问题。

### Q2：为什么不用 f2c、fable 这类源到源工具？

**参考答案：**

它们是重要基线和工具，不是敌人。f2c 主要面向 C，生成代码可读性和 C++ 现代风格有限；fable 等工具也有自己的覆盖范围和转换规则。我的项目价值不是替代所有 transpiler，而是提供“模型 + 编译器 + 测试 + 修复”的闭环，对失败样例进行诊断和修复，并输出可解释的映射说明。评测时我会把传统工具作为对照，而不是回避。

### Q3：为什么不直接 Prompt 或 RAG，为什么要微调？

**参考答案：**

Prompt 和 RAG 是基线，不是替代品。Prompt 能教会模型任务格式，RAG 能提供相似翻译和长尾规则，但它们都不改变模型内部行为。微调主要解决三件事：第一，让模型稳定输出 JSON 和 C++17 风格；第二，让模型学习“看到编译器错误后如何修”；第三，让领域术语和映射规则更一致。最终我会做 base、RAG、LoRA、LoRA+RAG 的对比，用数据证明微调增量。

### Q4：为什么选 Qwen2.5-Coder-7B-Instruct？

**参考答案：**

选型看六点：代码预训练能力、C++ 能力、结构化输出、LoRA/GGUF 生态、许可、硬件成本。Qwen2.5-Coder 在代码模型里兼顾能力和工具链成熟度；7B 在 A800 40GB 单卡上 bf16 LoRA 风险较低；同系列 tokenizer 和模板成熟，便于 Ollama 部署。更大的 14B/30B 不是不能做，而是不适合作为短周期 MVP 的第一选择。

### Q5：为什么不是 14B 或 30B？

**参考答案：**

A800 是单卡 40GB，不是单卡 80GB。7B bf16 权重约 14GB，加上 LoRA、激活和临时缓冲，单卡 40GB 比较稳。14B bf16 权重约 28GB，训练时加上激活和优化器状态会非常紧张，需要 QLoRA 或双卡 FSDP/DeepSpeed。30B MoE 虽然激活参数少，但权重、路由、训练框架和 GGUF 导出风险都更高。MVP 先用 7B 把数据、训练、部署、Agent、评测闭环跑通，再评估更大模型。

### Q5.1：为什么不是直接上 30B MoE？它不是只激活 3B 吗？

**参考答案：**

“激活参数少”不等于训练和部署免费。MoE 的总权重仍要存储，路由层和专家并行会引入额外复杂度；微调时优化器状态、通信和负载均衡也是成本；GGUF/Ollama 对 MoE 的支持和导出路径也要单独验证。对短周期项目，7B 稠密模型更稳。

### Q6：为什么本地 NUC 只做冒烟？

**参考答案：**

NUC 是 i7-7000，没有 NVIDIA CUDA GPU。2B Q4 模型可以 CPU 推理，适合验证 Ollama 接口、JSON 结构和 Agent 控制流，但训练 7B 不现实，推理速度也不适合做最终质量评测。因此本地负责快速反馈，A800 负责正式训练和评测。

### Q7：为什么首版选 F90/95，F77 只做兼容集？

**参考答案：**

这是数据易得性和短周期的取舍。F90/95 自由格式更规整，模块、函数和子程序接口清晰，便于解析、分块、自动生成测试驱动。F77 的固定格式、隐式类型、`COMMON`、`EQUIVALENCE`、`GOTO` 和格式化 I/O 会显著增加解析和语义映射难度。首版先用 F90/95 建立闭环，再保留少量 F77 样本展示 legacy 兼容意识。

### Q8：为什么 C++ 标准选 C++17？

**参考答案：**

C++17 在 GCC/Clang 生态中支持广泛，常见的 A800 训练环境和 Ubuntu 镜像都能直接编译。它已经具备结构化绑定、`if constexpr`、`std::optional`、`std::filesystem` 等足够能力。C++20 会引入编译器版本差异和额外教学成本，对短周期 MVP 不划算。第一版只依赖标准库，避免 Eigen、xtensor、OpenMP 的额外复杂度。

### Q9：数据从哪里来？

**参考答案：**

优先级是：宽松许可的公开数值代码、强模型合成、人工改写、Agent 失败轨迹、负样本。公开代码包括 Netlib、Rosetta Code、Fortran-lang 生态包、LAPACK 示例等；合成数据按语法点和映射规则定向生成，但必须经过 gfortran/g++ 双端编译、运行和输出对比。CodeNet、The Stack 等大规模语料只会作为后续扩展，先核验许可和语言标注。

### Q10：怎么保证合成数据质量？

**参考答案：**

合成数据不能只靠模型自评。我会做多层过滤：语法解析、Fortran 编译运行、C++ 编译运行、同输入输出对比、数值容差检查、去重、特征分层、人工抽检。失败的样本进入错误库，不直接进训练集。每个样本记录来源、许可、方言、特性、编译信息和验证状态。

### Q11：怎么避免数据泄漏？

**参考答案：**

按来源或项目切分，不随机按行切分；对源码做哈希去重、函数名归一化、空白归一化、n-gram 和嵌入相似度检查；冻结测试集并记录 SHA-256 和样本 ID；训练集和测试集不能来自同一仓库的连续子程序或同一模板变体。

### Q12：训练数据配比怎么设计？

**参考答案：**

MVP 建议：单轮翻译 60%–70%，修复样本 20%–30%，结构化输出 5%–10%，通用回放 5%–10%。修复样本来自“故意弄错或模型首轮失败 → 编译器错误 → 修复成功”的真实轨迹。负样本和不支持特性单独评测，不盲目塞进训练集。

### Q13：怎么构造修复样本？

**参考答案：**

先让模型翻译，收集编译或运行失败的真实错误，再用强模型或人工修复，最后把“原 Fortran + 错误 C++ + 编译器错误 + 修复版”作为一条样本。关键是错误必须来自真实编译器，而不是编造；修复后的版本必须重新编译和测试。

### Q14：评测指标有哪些？

**参考答案：**

JSON 有效率、编译成功率、链接成功率、测试通过率、数值等价率、平均迭代数、修复成功率、pass@k、token 消耗、延迟、通用能力回归。报告时区分 L0 编译、L1 测试、L2 数值等价、L3 边界、L4 人工复核，不能把编译通过说成翻译正确。

### Q15：为什么不能宣称语义等价？

**参考答案：**

测试只能证明在给定输入和容差下输出一致，不能证明对所有输入等价。浮点运算顺序、编译器优化、NaN/Inf、未定义行为都会造成差异。我会明确说“差异测试”或“给定测试集上的数值等价”，不宣称形式化语义等价。

### Q16：Agent 的核心流程是什么？

**参考答案：**

`preprocess → translate → compile_reference → compile_candidate → run_compare → diagnose → repair → guard → finalize`。编译器错误和数值差异是外部反馈，模型只负责单步翻译或修复，LangGraph 负责状态流转、重试和终止。

### Q17：为什么用 LangGraph，不用简单 while 循环？

**参考答案：**

简单 while 循环适合原型，但状态、条件边、错误历史、预算、震荡检测和可观测性很快会变得混乱。LangGraph 把 State、Node、Edge 显式化，便于测试、扩展和解释；即使不用 LangGraph，也应该有等价的状态机设计。

### Q18：沙箱安全怎么保证？

**参考答案：**

生成的代码不能直接在宿主机运行。沙箱用 Docker，断网、只读根文件系统、非 root、内存/CPU/超时限制，先编译后运行，限制文件系统挂载范围，记录完整执行轨迹。高风险代码只做静态检查，不执行。

### Q19：Agent 死循环怎么办？

**参考答案：**

最大迭代次数、相邻代码相似度震荡检测、错误重复检测、token/时间预算、历史最佳版本兜底。达到上限时返回最佳版本和完整错误轨迹，标记 `max_iter_reached`，不能假装成功。

### Q20：长 Fortran 文件怎么处理？

**参考答案：**

按模块或过程切块，先生成接口和类型映射，为每个过程单独编译和测试，再做链接测试。跨过程全局状态单独建模。超出能力时标记未翻译或高风险，不把长代码硬塞进一个上下文。

### Q21：目前最大的技术风险是什么？

**参考答案：**

数据质量是最大风险。Fortran 长尾语法复杂，合成数据可能有系统性错误；7B 模型修复能力也有限。对策是双端编译执行验证、人工抽检、传统工具对照、从 30–50 条种子集开始，逐步扩大，不把未验证数据直接投入训练。

### Q22：如果效果不如强模型 API，项目还有价值吗？

**参考答案：**

有。项目目标是本地、可控、低成本、可解释的完整链路，不是单纯追求绝对质量。强模型 API 可以作为教师和数据合成工具，也可以作为上界基线。我们报告性价比、修复收益、部署成本和失败边界。

### Q23：这个项目怎么用于简历？

**参考回答：**

简历上写三个点：第一，领域 LoRA 微调与数据验证流水线；第二，编译/运行/数值对比的多轮自修复 Agent；第三，从训练到 GGUF/Ollama 的完整部署闭环。数字只写真实跑出来的，不写预期数字。

## 2. Transformer 架构八股

### Q24：Transformer 的整体结构是什么？

**参考答案：**

原始 Transformer 是 encoder-decoder 结构，每层包含多头自注意力、前馈网络、残差连接和归一化。Encoder 做双向注意力，Decoder 做因果掩码注意力并 cross-attend 到 encoder。现代大语言模型大多是 decoder-only，只保留因果自注意力、FFN、残差和归一化，训练目标是自回归下一 token 预测。

### Q25：Self-Attention 的公式是什么？

**参考答案：**

\[
\text{Attention}(Q,K,V)=\text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
\]

其中 \(Q=XW_Q\)、\(K=XW_K\)、\(V=XW_V\)。先用 Q 和 K 的点积算相关性，除以 \(\sqrt{d_k}\) 做缩放，softmax 得到权重，再对 V 加权求和。

### Q26：为什么要除以 \(\sqrt{d_k}\)？

**参考答案：**

如果 Q、K 各维独立且方差为 1，点积的方差会随维度 \(d_k\) 线性增长。维度越大，点积绝对值越大，softmax 越容易进入饱和区，梯度变小。除以 \(\sqrt{d_k}\) 可以把方差拉回大致稳定范围，改善训练稳定性。

### Q27：Q、K、V 分别代表什么？

**参考答案：**

Q 是 query，表示当前位置想“查询什么”；K 是 key，表示每个位置能“提供什么索引”；V 是 value，表示每个位置实际“携带什么信息”。注意力权重由 Q 和 K 决定，输出是 V 的加权和。它们都是输入通过可学习线性投影得到的。

### Q28：Multi-Head Attention 为什么要多头？

**参考答案：**

单个注意力头只能在一个投影子空间里建模关系。多头把 \(d_{model}\) 拆成多个子空间，每个头独立做注意力，再拼接并投影。不同头可以关注语法、位置、指代、局部或长距离等不同模式，提高表达能力。

### Q29：多头注意力的计算复杂度是多少？

**参考答案：**

自注意力对序列长度 \(n\) 的时间和显存复杂度是 \(O(n^2d)\)，其中 \(d\) 是表示维度。序列长度翻倍，注意力矩阵大致变成四倍，这是长上下文成本高的根本原因。FlashAttention 优化的是 IO 和显存，不改变理论复杂度。

### Q30：位置编码有哪些方案？

**参考答案：**

常见有正弦位置编码、可学习位置编码、相对位置编码、RoPE、ALiBi。现代 Llama/Qwen 系常用 RoPE：对 Q/K 做旋转，使注意力自然携带相对位置信息。长上下文扩展常用位置插值、NTK-aware、YaRN 等方法。

### Q31：RoPE 的核心思想是什么？

**参考答案：**

RoPE 把位置信息编码成旋转矩阵，对 Q 和 K 的不同维度按位置角度旋转。两个 token 的注意力分数只依赖它们的相对位置差，因此比绝对位置编码更适合外推，也方便做上下文扩展。

### Q32：为什么现代大模型大多是 decoder-only？

**参考答案：**

decoder-only 结构统一、训练目标简单，适合大规模自回归预训练和零样本/少样本泛化；同一套模型可以做生成、对话、代码和工具调用。Encoder-decoder 在翻译、摘要等 seq2seq 任务上仍有优势，但大语言模型主流选择 decoder-only。

### Q33：Causal Mask 是什么？

**参考答案：**

Causal mask 是下三角掩码，保证位置 \(t\) 只能看到 \(1\) 到 \(t\) 的 token，不能看到未来 token。训练时并行计算所有位置的下一 token 预测，但通过掩码保持自回归性质。Padding mask 则用于屏蔽无效填充 token，两者经常组合。

### Q34：FFN 在 Transformer 里做什么？

**参考答案：**

FFN 对每个位置独立做两层线性变换和非线性激活，通常先升维再降维。它负责非线性特征变换和知识存储，参数量往往占模型很大比例。现代模型常用 SwiGLU：\(FFN(x)=W_2(\text{Swish}(W_1x)\odot W_3x)\)，比普通 ReLU MLP 表达更强，但参数也更多。

### Q35：残差连接和归一化为什么重要？

**参考答案：**

残差连接让梯度可以跨层直接回传，缓解深层网络的退化和梯度消失；归一化稳定激活分布，加速收敛。现代 LLM 多用 pre-norm：先归一化再进入子层，再和残差相加，训练更稳定。

### Q36：LayerNorm 和 RMSNorm 有什么区别？

**参考答案：**

LayerNorm 对特征做均值中心和方差归一化；RMSNorm 只除以均方根，不减均值，也不一定有 bias。RMSNorm 计算更简单，在现代 LLM 中效果稳定，Llama/Qwen 系常用。两者都属于归一化策略，不是模型能力的根本差异。

### Q37：KV Cache 是什么？

**参考答案：**

自回归生成时，历史 token 的 K、V 不会变化，可以缓存起来，下一步只计算新 token 的 Q，并复用历史 K/V，避免重复计算。KV Cache 用显存换计算，是推理加速的关键。长上下文和大 batch 下，KV Cache 会成为主要显存占用。

### Q38：MHA、MQA、GQA 有什么区别？

**参考答案：**

MHA 每个 query head 都有独立 K/V head；MQA 所有 query head 共享一组 K/V；GQA 介于两者之间，把 query head 分组共享 K/V。GQA 能显著减少 KV Cache 和带宽，同时比 MQA 保留更多表达能力，是当前大模型常见选择。

### Q39：FlashAttention 是什么？是近似注意力吗？

**参考答案：**

FlashAttention 是 IO-aware 的精确注意力实现。它通过分块、在线 softmax 和重计算，把注意力计算尽量留在 SRAM，减少 HBM 读写，从而加速并降低显存占用，不改变注意力数学结果。它不是稀疏或近似注意力。

### Q40：上下文窗口为什么不能无限增大？

**参考答案：**

第一，注意力计算和显存是 \(O(n^2)\)；第二，位置编码外推能力有限；第三，训练数据里长依赖样本不足；第四，KV Cache 随序列线性增长。扩大上下文需要位置编码扩展、长文本训练数据、显存优化和评测配套。

### Q41：Tokenization 是什么？

**参考答案：**

Tokenization 把文本切成子词单元，再映射为整数 ID。常见方法有 BPE、WordPiece、SentencePiece 和 Unigram。代码模型通常对缩进、符号、下划线和常见标识符做专门切分。Tokenizer 的词表和特殊 token 必须与基座模型匹配，否则 embedding 和输出层会错位。

### Q42：Chat Template 为什么重要？

**参考答案：**

Chat template 定义 system、user、assistant 等角色的特殊 token 和边界。训练和推理必须使用同一模板，否则模型看到的格式分布不一致，会出现答非所问、格式漂移或 EOS 异常。微调时通常只对 assistant 回复计算 loss，需要对 prompt token 做 loss mask。

### Q43：预训练目标有哪些？

**参考答案：**

常见有 causal language modeling，也叫 next-token prediction，用于 GPT/LLaMA/Qwen；masked language modeling 用于 BERT 类 encoder；span corruption 用于 T5 类 encoder-decoder。代码模型通常用 causal LM，在代码语料上继续预训练或指令微调。

### Q44：MoE 是什么？

**参考答案：**

MoE 是 Mixture of Experts。每层有多个 FFN 专家和一个 router，每个 token 只激活 top-k 个专家，因此总参数量可以很大，但每个 token 的计算量相对小。代价是路由负载均衡、通信、训练稳定性和部署复杂度。Qwen3-Coder-30B-A3B 就是总参数约 30B、激活约 3B 的 MoE 代表。

### Q45：为什么长上下文训练和推理成本高？

**参考答案：**

注意力矩阵大小随 \(n^2\) 增长；KV Cache 随 \(n\) 线性增长；长序列还会增加激活和通信。训练时通常需要序列并行、FlashAttention、梯度检查和分块；推理时需要 PagedAttention、KV 量化和批处理调度。

### Q46：Transformer 相比 RNN/CNN 的优势是什么？

**参考答案：**

Transformer 可以在序列位置间并行计算，长距离依赖路径更短，训练更容易扩展；RNN 有顺序依赖，长程记忆和并行性受限；CNN 局部感受野需要堆叠很多层才能覆盖长距离。Transformer 的代价是 \(O(n^2)\) 注意力和较高显存。

### Q47：Scaling Law 是什么？

**参考答案：**

Scaling law 描述模型参数量、数据量、计算量和 loss 之间的经验关系。通常在一定范围内，三者同步增加会带来可预测的 loss 下降。它指导预算分配，但不保证下游任务线性提升，代码任务还需要数据质量、领域匹配和评测。

### Q48：涌现能力是什么？

**参考答案：**

一些能力在模型规模、数据或训练方法达到某个阶段后表现明显提升，例如多步推理、工具使用和上下文学习。严格来说，部分“涌现”可能受指标和阈值影响，但工程上要关注模型规模与任务能力的非线性关系。

### Q49：In-Context Learning 和微调有什么区别？

**参考答案：**

In-context learning 把示例放在 prompt 里，不改权重，适合快速适配和知识注入；微调改变参数，适合稳定行为、格式和领域风格。上下文学习受上下文长度和推理成本限制，微调受数据质量和灾难性遗忘限制，两者可以组合。

### Q50：模型为什么会幻觉？

**参考答案：**

幻觉来自训练数据噪声、知识截止、概率生成机制、缺乏外部验证和采样随机性。代码任务里表现为生成不存在的 API、遗漏 include、数组越界或编造库函数。缓解手段包括 RAG、结构化输出、编译执行、单元测试、约束解码和多轮修复。

### Q51：Temperature、Top-k、Top-p 分别是什么？

**参考答案：**

Temperature 缩放 logits，控制分布平滑程度；Top-k 只保留概率最高的 k 个 token；Top-p 保留累计概率达到 p 的最小集合。低 temperature 更确定，适合代码；高 temperature 更多样，适合创意。代码翻译通常用低 temperature，再加编译测试验证。

### Q52：Beam Search 和采样有什么区别？

**参考答案：**

Beam Search 保留多个候选序列，追求高概率路径，适合确定性生成，但可能重复、缺乏多样性且成本高。采样按概率随机选择，适合开放生成。代码任务常用低温度采样或贪心，再用编译器和测试筛选。

### Q53：FP16、BF16、FP32 有什么区别？

**参考答案：**

FP32 精度最高但显存和带宽成本大；FP16 精度高但动态范围小，容易溢出；BF16 指数范围与 FP32 接近，尾数少，训练更稳定，适合 A800 等支持 BF16 的 GPU。LLM 训练通常优先 BF16，推理可进一步量化。

### Q54：量化有哪些类型？

**参考答案：**

训练侧有 QLoRA 的 NF4；推理侧有 GPTQ、AWQ、GGUF 的 Q4/Q5/Q8 等。GPTQ/AWQ 常用于 GPU 权重-only 量化；GGUF 适合 llama.cpp/Ollama，CPU/GPU 混合推理方便。量化会带来质量损失，必须通过下游评测而不是只看 perplexity。

### Q55：KV Cache 显存怎么估算？

**参考答案：**

近似公式：

\[
\text{KV bytes} \approx 2 \times L \times H_{kv} \times d_{head} \times n \times B \times \text{bytes per element}
\]

其中 2 表示 K 和 V，L 是层数，\(H_{kv}\) 是 KV head 数，\(d_{head}\) 是 head 维度，n 是序列长度，B 是 batch。GQA 的作用就是减少 \(H_{kv}\)。

### Q56：Transformer 的主要局限是什么？

**参考答案：**

注意力复杂度高、长上下文成本大、缺乏显式符号推理、对训练分布外样本脆弱、幻觉难以完全消除、推理需要大量计算和显存。工程上要用检索、工具、验证器和沙箱弥补这些局限。

## 3. 微调策略八股

### Q57：预训练、继续预训练、SFT 有什么区别？

**参考答案：**

预训练是在大规模通用语料上学习语言和世界知识；继续预训练是在领域语料上继续做自回归训练，常用来注入领域分布；SFT 是在指令-回答数据上做监督微调，让模型学会遵循任务格式。这个项目主要用 SFT，数据是“Fortran + 指令 → JSON + C++”，必要时才考虑继续预训练。

### Q58：全参微调和 PEFT 有什么区别？

**参考答案：**

全参微调更新所有参数，表达能力强、成本最高、灾难性遗忘风险也最大；PEFT 只训练少量额外参数或低秩增量，显存和存储成本低、可插拔、对小数据集更稳。工业应用中 LoRA/QLoRA 是主流折中，本项目 MVP 选 PEFT。

### Q59：LoRA 的数学形式是什么？

**参考答案：**

原来权重是 \(W_0\in\mathbb{R}^{d\times k}\)。LoRA 不直接更新 \(W_0\)，而是学习低秩增量：

\[
W = W_0 + \Delta W = W_0 + \frac{\alpha}{r}BA
\]

其中 \(B\in\mathbb{R}^{d\times r}\)，\(A\in\mathbb{R}^{r\times k}\)，且 \(r\ll\min(d,k)\)。前向可以写成 \(h=W_0x+\frac{\alpha}{r}B(Ax)\)。训练时 \(W_0\) 冻结，只训练 A、B。

### Q60：LoRA 的 rank、alpha、dropout 分别怎么选？

**参考答案：**

rank 决定低秩增量容量：`r=8/16` 适合小任务，`r=32/64` 适合代码、领域适配和多任务。alpha 控制增量缩放，常见 `alpha=r` 或 `alpha=2r`，本项目基线用 `r=32, alpha=64`。dropout 用在 LoRA 输入上防过拟合，常见 0.05，数据少时可适当增大。

### Q61：LoRA 的 target modules 怎么选？

**参考答案：**

只调 `q_proj/v_proj` 是最省参数的起点；代码任务通常覆盖注意力层的 `q/k/v/o_proj` 和 MLP 层的 `gate/up/down_proj`，即 `all-linear`。覆盖面越大，容量越强，显存和训练成本也越高。具体效果要靠验证集消融，而不是凭经验拍脑袋。

### Q62：LoRA 初始化为什么 B 常为零？

**参考答案：**

如果 B 初始为 0，A 随机初始化，那么 \(\Delta W=BA=0\)，训练开始时模型行为与基座完全一致，不会突然破坏预训练能力。之后梯度逐步学习增量。A、B 的角色可以交换，但关键是保证初始增量为零。

### Q63：LoRA 怎么合并？

**参考答案：**

推理时可以把 \(\Delta W=(\alpha/r)BA\) 加回 \(W_0\)，得到合并后的权重，部署时不需要额外的 LoRA 分支。合并要求模型结构和 tokenizer 一致；合并后可以继续做量化、GGUF 转换和 Ollama 部署。合并是不可逆的，要保留 adapter 和基座版本记录。

### Q64：QLoRA 是什么？

**参考答案：**

QLoRA 是 4bit 量化基座 + LoRA 的微调方法。基座权重用 NF4 量化并冻结，前向计算时反量化到 bf16，LoRA 适配器保持可训练。它显著降低权重显存，使 14B/30B 级模型可以在单卡或双卡上微调。

### Q65：QLoRA 的 NF4、双重量化、paged optimizer 分别是什么？

**参考答案：**

NF4 是针对近似正态分布权重设计的信息论最优 4bit 数据类型；双重量化对量化常数再量化，进一步节省显存；paged optimizer 用统一内存分页处理优化器状态峰值，避免瞬时 OOM。它们共同降低显存，但不是免费的：反量化有计算开销，量化也可能带来质量损失。

### Q66：QLoRA 和 bf16 LoRA 怎么选？

**参考答案：**

如果显存足够，优先 bf16 LoRA，训练更稳定、量化误差更小。A800 40GB 对 7B bf16 LoRA 比较合适，所以 MVP 用 bf16 LoRA。14B/30B 或显存不足时用 QLoRA。报告里要把 QLoRA 定位为工程折中，不能声称无损。

### Q67：DoRA、LoRA+、rsLoRA、PiSSA 是什么？

**参考答案：**

DoRA 把权重分解为幅度和方向，对方向做低秩更新；LoRA+ 给 A、B 设置不同学习率，提高收敛；rsLoRA 对 rank 缩放做修正，改善大 rank 稳定性；PiSSA 用 SVD 初始化 LoRA 子空间，让初始更新不是零。它们是 LoRA 的改进变体，本项目 MVP 先用标准 LoRA，后续可做消融。

### Q68：Adapter、Prefix Tuning、Prompt Tuning、IA3 有什么区别？

**参考答案：**

Adapter 在层间插入小瓶颈模块；Prefix/Prompt Tuning 在激活或输入前加可训练前缀/软提示；IA3 对激活做可学习缩放。它们都比 LoRA 更省参数，但表达能力、推理合并和生态支持不同。代码任务上 LoRA 生态最成熟，因此优先。

### Q69：RLHF、PPO、DPO、ORPO、KTO、GRPO 分别是什么？

**参考答案：**

RLHF 是用人类偏好训练奖励模型，再用 PPO 等策略优化；DPO 直接用偏好对做对比优化，不需要显式奖励模型；ORPO 把 SFT 和偏好优化结合；KTO 用二元反馈而不是成对偏好；GRPO 是组相对策略优化，用组内相对奖励估计优势，在推理模型里常用。代码翻译项目 MVP 先做 SFT，后续可用 DPO/GRPO 优化“能编译、测试通过”的偏好。

### Q70：SFT、DPO、RLHF 的适用场景有什么不同？

**参考答案：**

SFT 适合教格式、风格和基本能力；DPO 适合有成对好坏样本、想要偏好对齐；RLHF/PPO 适合有稳定奖励模型、需要在线探索的场景，但工程复杂。对 Fortran→C++，编译/测试通过与否天然可转成偏好信号，DPO 比 PPO 更轻量，适合二期。

### Q71：RAG 和微调怎么选？

**参考答案：**

RAG 适合注入可检索的知识和最新规则，例如常见 Fortran→C++ 映射、错误修复案例；微调适合改变模型的输出风格、格式稳定性和单步能力。两者不冲突。本项目先测 RAG 基线，再做 LoRA，最后可做 LoRA+RAG 消融。

### Q72：什么是灾难性遗忘？怎么缓解？

**参考答案：**

灾难性遗忘是模型在新领域数据上微调后，原有通用能力下降。缓解方法包括混入通用回放数据、降低学习率、减少 epoch、使用 LoRA/QLoRA、只训练部分模块、保存基座对照、在通用代码任务上做回归评测。本项目会混入 5%–10% 通用代码/指令回放。

### Q73：数据质量和数量哪个更重要？

**参考答案：**

对领域微调，质量优先。1000 条经过编译、执行、去重和人工抽检的样本，通常比 10 万条未经校验的合成代码更有价值。数量用于覆盖长尾和稳定泛化，但脏数据会把错误模式直接训进模型。

### Q74：怎么判断过拟合还是欠拟合？

**参考答案：**

训练 loss 继续下降、验证 loss 上升或下游编译率下降，通常是过拟合；训练和验证 loss 都高、编译率低，通常是欠拟合或数据/任务不匹配。处理过拟合要降 epoch、加 dropout、加数据、做去重；处理欠拟合要增加模型容量、提高 rank、改善数据覆盖或调整学习率。

### Q75：微调超参怎么设？

**参考答案：**

LoRA 常用 LR 1e-4 到 2e-4、cosine schedule、warmup 3%–5%、2–3 epoch、bf16、gradient checkpointing。7B 单卡 micro batch 2–4，gradient accumulation 8–16。rank 从 16 或 32 起，alpha 取 2r，dropout 0.05。最终以验证集编译率和测试通过率选参数，不只看 loss。

### Q76：Loss Mask 是什么？

**参考答案：**

在 SFT 中，prompt 部分通常不计算 loss，只对 assistant 回复部分计算交叉熵。做法是把 prompt 对应的 label 设为 -100，训练框架会忽略这些位置。这样可以避免模型学习“复述问题”，把容量集中在目标回答上。

### Q77：Packing 是什么？有什么风险？

**参考答案：**

Packing 把多个短样本拼接到接近 max_len，减少 padding 和计算浪费。风险是不同样本之间可能互相 attend，必须用正确的 attention mask 或 FlashAttention varlen/block-diagonal mask 隔离。否则样本边界会被污染，训练信号变差。

### Q78：梯度累积和增大 batch 有什么区别？

**参考答案：**

梯度累积在多个 micro batch 上累加梯度再更新，近似增大 global batch，但不改变单次前向激活显存；增大 micro batch 会直接增加激活显存和吞吐。显存不足时用梯度累积，显存充足时适当增大 micro batch 提高 GPU 利用率。

### Q79：Gradient Checkpointing 是什么？

**参考答案：**

前向时只保存部分激活，反向需要时重新计算，用计算换显存。它能显著降低长序列训练的激活占用，但会增加约 20%–30% 训练时间。7B 长序列 LoRA 通常建议开启。

### Q80：DDP、FSDP、ZeRO 有什么区别？

**参考答案：**

DDP 每张卡复制完整模型，反向做梯度 all-reduce，显存不省；FSDP 把参数、梯度和优化器状态分片到各卡，按需 all-gather，适合大模型；DeepSpeed ZeRO-1/2/3 分别分片优化器状态、梯度、参数。2×A800 40GB 做 7B LoRA 用 DDP 足够，14B 或更大模型再考虑 FSDP/ZeRO。

### Q81：7B 全参微调需要多少显存？

**参考答案：**

7B bf16 权重约 14GB；如果 Adam 全参，优化器状态 fp32 约 56GB，梯度约 14GB，再加激活，总需求通常超过 84GB。2×A800 40GB 可以用 FSDP/ZeRO-3 分片，但工程复杂。LoRA 只训练适配器，优化器状态极小，因此更适合 40GB 单卡。

### Q82：7B bf16 LoRA 的显存大致怎么组成？

**参考答案：**

基座 bf16 约 14GB；LoRA 参数、梯度和优化器状态通常几百 MB 到 1–2GB；激活受 batch、序列长度、层数和是否 checkpointing 影响，可能 8–15GB；再加 CUDA、通信和碎片，总占用约 24–32GB，留出余量给长序列和临时峰值。

### Q83：14B 在 40GB 上怎么做？

**参考答案：**

14B bf16 权重约 28GB，单卡 40GB 做 bf16 LoRA 很紧张，通常需要 QLoRA，把基座压到 4bit，约 7–8GB，再训练 LoRA；或者用两张 A800 + FSDP/DeepSpeed 分片。MVP 不做，等 7B 闭环跑通后再评估。

### Q84：训练 loss 突然 spike 怎么办？

**参考答案：**

先检查数据中是否有极长样本、异常 token、重复样本或格式错误；再检查学习率、warmup、gradient clipping、bf16 溢出和 batch。处理手段包括跳过异常 batch、降低 LR、增大 warmup、加 grad clip、恢复最近 checkpoint。不要盲目重跑整个训练。

### Q85：训练时看哪些指标？

**参考答案：**

训练/验证 loss、学习率、梯度范数、显存峰值、吞吐；下游 JSON 有效率、编译成功率、测试通过率、修复成功率、截断率和重复率。loss 只说明拟合，不说明代码能否编译，必须有下游评测。

### Q86：怎么做模型合并？

**参考答案：**

先 merge LoRA adapter 得到完整 HF 模型；如果有多个同源微调模型，可以做权重平均、SLERP、TIES、DARE 等模型合并。合并前要确认 tokenizer、模型结构和训练配置一致，并用评测集验证，不能只看 loss。

### Q87：QAT 和 QLoRA 是一回事吗？

**参考答案：**

不是。QLoRA 是训练时冻结 4bit 基座、训练 LoRA；QAT 是量化感知训练，在训练前向/反向中模拟量化误差，让模型适应低精度。QLoRA 更省显存、更简单；QAT 工程复杂但可能获得更好的量化后精度。

### Q88：长上下文微调有什么注意事项？

**参考答案：**

先确认位置编码扩展方法和基座最大长度；训练数据要真实覆盖长依赖；注意激活显存和 attention 复杂度；使用 FlashAttention、梯度检查、序列并行；评测要覆盖长上下文检索、跨函数引用和全局状态。不能只把 max_len 调大。

### Q89：多任务微调怎么配比？

**参考答案：**

先定义明确任务簇：翻译、修复、结构化输出、通用回放。按验证集表现动态调整配比，保证每个任务都有足够样本。避免一个任务压倒其他任务；可以用 temperature sampling 或分阶段课程学习。

### Q90：如何避免数据污染？

**参考答案：**

训练数据记录来源；测试集冻结；做源码哈希、n-gram、MinHash、嵌入相似度检查；同名函数、同仓库、同模板变体按来源隔离；训练前输出数据卡，训练后检查测试样本是否在训练分布中高相似。

### Q91：怎么选基座模型？

**参考答案：**

看代码能力、目标语言覆盖、tokenizer 和 chat template、上下文长度、LoRA/QLoRA 生态、GGUF 导出、许可证、显存和推理成本。Fortran 是小众语言，代码模型不一定见过大量 Fortran，所以数据质量比模型参数更重要。

### Q92：什么时候不该微调？

**参考答案：**

如果任务可以通过 Prompt、RAG、规则引擎或传统编译器解决，就不应优先微调；如果数据不足、质量不可控、评测没建立、推理成本不可接受，也不应微调。微调是改变行为的重手段，先证明基线和规则上限。

### Q93：怎么评测微调模型？

**参考答案：**

固定测试集，比较 base few-shot、RAG、LoRA、LoRA+RAG；指标包括 JSON 有效率、编译率、测试通过率、数值等价率、修复率、迭代数、token 和延迟；报告置信区间和失败分布；做 rank、数据量、量化、max_len 的消融。

### Q94：adapter 怎么部署？

**参考答案：**

两种形态：运行时挂 adapter，或 merge 后量化成 GGUF。前者便于多任务切换但依赖框架支持；后者单文件、稳定、适合 Ollama。本项目主路线是 merge → GGUF Q4_K_M → Ollama，保留 HF 格式用于评测和复现。

### Q95：量化会带来什么影响？

**参考答案：**

量化降低显存和带宽，提高 CPU/边缘部署可行性，但会带来数值误差，可能影响代码生成、长尾推理和格式稳定性。必须做 Q4/Q5/Q8 对照，报告编译率、测试通过率和数值差异，不能只看模型能不能启动。

### Q96：模型蒸馏和微调有什么关系？

**参考答案：**

蒸馏是让学生模型拟合教师模型的输出分布或隐藏状态，适合把大模型能力压缩到小模型；微调是让学生在目标任务数据上学习。实践中可以先用强模型合成数据，再在小模型上做 SFT/蒸馏式训练，本项目的数据合成就带有教师-学生色彩。

## 4. Agent 与系统设计

### Q97：LangGraph 和 ReAct 有什么区别？

**参考答案：**

ReAct 是一种提示/推理模式，让模型交替 reasoning 和 acting；LangGraph 是显式状态机框架，用 State、Node、Edge 和条件分支描述控制流。这个项目更适合 LangGraph，因为编译、运行、比较、修复是有明确阶段和终止条件的工程流程，不需要让模型自由决定所有控制流。

### Q98：小模型怎么做工具调用？

**参考答案：**

不依赖原生 function calling，而是用 JSON schema + few-shot + 解析失败重试。模型只负责输出结构化动作或代码，工具层负责校验、执行和错误回传。微调可以显著提高 JSON 稳定性和修复能力。

### Q99：工具怎么设计？

**参考答案：**

工具要有明确输入输出、超时、错误码和可观测性。编译器工具返回结构化错误；运行工具返回 exit code、stdout、stderr；比较工具返回差异和容差；检索工具返回相似样例和规则。工具不信任模型输出，所有参数都要校验。

### Q100：编译器错误怎么分类？

**参考答案：**

分为语法错误、类型/转换错误、链接错误、运行时崩溃、超时、数值偏差和语义差异。先解析 line number、column、severity、error code，再映射到修复策略。不同类别走不同 prompt，比一个通用“修复一下”更有效。

### Q101：Repair Prompt 怎么写？

**参考答案：**

结构是：原始任务 + 当前代码 + 最近 2 轮错误 + 修复要求 + 输出 JSON schema。只带最近错误，防止上下文膨胀；明确要求不能删除测试、不能伪造通过、不能省略不支持项。修复后必须重新编译和测试。

### Q102：RAG 在代码翻译里怎么做？

**参考答案：**

把 Fortran→C++ 平行对、映射规则、常见编译器错误修复案例建成检索库。按方言、特性、函数签名、代码结构过滤，再用 BM25/代码嵌入做 hybrid retrieval。检索内容注入 prompt，但不能替代编译验证。

### Q103：沙箱为什么要断网、只读、限资源？

**参考答案：**

模型可能生成删除文件、下载依赖、fork 炸弹、无限循环或越界访问的代码。断网防止外联，只读防止破坏宿主，非 root 降权，内存/CPU/超时限制资源，挂载目录限制 I/O。沙箱是执行不可信代码的最低要求。

### Q104：Agent 怎么做可观测性？

**参考答案：**

每轮记录输入代码、生成代码、diff、编译命令、stdout/stderr、测试结果、错误分类、token、耗时、迭代号和终止原因。最好用 trace 形式串起来，便于复现、错误分析和答辩演示。

### Q105：Agent 怎么评测？

**参考答案：**

除了单次翻译指标，还要看最终成功率、平均迭代数、修复率、首次失败到成功的比例、震荡率、超时率、token 成本和每轮收益。对比 base、LoRA、LoRA+Agent，才能说明 Agent 是否真的带来增量。

### Q106：要不要多 Agent？

**参考答案：**

MVP 不需要。多 Agent 会增加通信、状态同步和不可控性。这个任务更适合单 Agent、显式状态机和多工具。只有当翻译、测试生成、代码审查等子任务有明显独立性和并行收益时，才考虑多 Agent。

### Q107：人类在环怎么做？

**参考答案：**

高风险特性、反复失败、低置信度或涉及外部依赖时，输出给人工确认；人工可以批准修复、提供测试、标记不支持或终止。生产中不让 Agent 自动提交代码，先生成 diff 和验证报告。

### Q108：延迟和成本怎么优化？

**参考答案：**

缓存相似翻译和编译结果；按过程切块减少上下文；并发执行互不依赖的测试；用小模型做错误分类和大模型做修复；限制 max_new_tokens；量化推理；对失败样本设预算和早停。

### Q109：生产部署为什么不能只用 Ollama？

**参考答案：**

Ollama 适合本地开发和单机部署，但生产还需要并发调度、监控、版本管理、权限、限流、灰度、回滚和 GPU 资源池。可以把 Ollama 作为原型和边缘推理，生产用 vLLM/TGI/Triton 等推理服务，再接入 Agent 平台。

## 5. 高压追问与陷阱问题

### Q110：7B 模型是不是太小了，真的能翻译 Fortran 吗？

**参考回答：**

单靠 7B 当然不能覆盖所有 Fortran，但我的目标不是通用替代，而是限定 F90/95 数值子集，用高质量领域数据、结构化输出、编译器和测试闭环提高可靠性。7B 的价值是成本、可部署和可复现；14B/30B 放在后续质量分支，不在 MVP 里混谈。

### Q111：会不会只是把训练集背下来了？

**参考回答：**

会有这个风险，所以测试集按来源和项目隔离，做哈希、n-gram 和嵌入近重复检查；训练/测试不随机切分；报告失败分布和未见特性的表现。仅凭 loss 不能证明泛化。

### Q112：合成数据本身错了怎么办？

**参考回答：**

合成数据不是真值来源，编译器和测试才是。每条样本必须双端编译运行，失败样本进入错误库；人工抽检；负样本和不支持项单独处理。老师模型只负责生成候选，不负责最终裁决。

### Q113：你的评测集太小，结论可信吗？

**参考回答：**

MVP 的 50–150 条只用于发现问题和验证闭环，不宣称统计显著。后续扩到 200–500 条并分层覆盖，使用 paired bootstrap 和置信区间，报告失败样本，不拿小数点后两位做过度解读。

### Q114：编译器通过就代表翻译正确吗？

**参考回答：**

不代表。编译只是 L0。正确性还要看测试、数值等价、边界条件和人工复核。我会明确分层报告，不把 L0 说成 L4。

### Q115：测试通过但语义错怎么办？

**参考回答：**

这是差异测试的固有局限。对策包括增加测试覆盖、边界输入、随机化输入、数值容差和人工抽检；对高风险特性标记不支持或人工复核。不会宣称形式化等价。

### Q116：你用强模型合成数据，算不算作弊？

**参考回答：**

教师模型用于数据生产是常见做法，关键是要披露、验证和去偏。学生模型的训练数据、评测隔离和推理成本都要单独报告；强模型也会作为上界基线，不会把教师能力算成学生能力。

### Q117：GPL/AGPL 代码能不能拿来微调？

**参考回答：**

许可风险需要逐项确认。MVP 优先使用 MIT/BSD/Apache/public-domain 和合成数据，记录来源与 license。GPL/AGPL 数据不进入可再分发训练集，除非法律和项目政策明确允许。最终交付不提供法律保证，但要有数据卡和许可清单。

### Q118：模型生成了不安全代码怎么办？

**参考回答：**

不直接在宿主机执行；Docker 沙箱断网、只读、非 root、限资源；静态扫描危险 API；高风险代码只做审查不执行；输出给人工确认。安全默认是拒绝执行不确定代码。

### Q119：Ollama 能上生产吗？

**参考回答：**

Ollama 很适合本地、单机和原型，但生产要考虑并发、监控、限流、版本和资源池。我的 MVP 用 Ollama 验证部署链路；生产可以用 vLLM/TGI/Triton，Ollama 作为边缘或本地推理层。

### Q120：为什么不用 Copilot/Claude 直接翻译？

**参考回答：**

通用模型是重要基线和教师，但项目目标是本地、可控、可审计、可验证的迁移流程。通用模型不能替代编译执行、数值对比、沙箱和项目级上下文；而且成本和隐私在工业场景里很关键。

### Q121：编译器错误信息会误导模型怎么办？

**参考回答：**

编译器错误是强信号但不总是根因。diagnose 节点会分类、去重、只保留最近错误，并让修复节点重新编译验证。若连续失败或错误重复，触发震荡检测和人工兜底。

### Q122：Fortran 特性太老、太偏怎么办？

**参考回答：**

首版明确覆盖 F90/95 子集，F77 只做兼容样本；`COMMON`、`EQUIVALENCE`、复杂指针、OpenMP/MPI 标记为二期或高风险。遇到不支持项要返回 `unsupported`，不能硬编。

### Q123：浮点结果不一致怎么办？

**参考回答：**

浮点差异是客观的。使用相对+绝对容差、NaN/Inf 规则、统一优化级别和多次运行；对不可约简的差异做人工分析，并在报告中说明。不能把浮点差异简单等价为翻译错误。

### Q124：Agent 会不会一直修不好？

**参考回答：**

会，所以有最大迭代、预算、震荡检测和错误重复检测；达到上限时返回历史最佳版本和完整错误轨迹，标记失败。Agent 不是保证成功，而是保证可控、可观测和可回退。

### Q125：你个人在这个项目里做了什么？

**参考回答：**

我负责问题定义、翻译契约、数据规范与验证、LoRA 训练方案、Ollama/GGUF 部署、LangGraph 状态机、沙箱、评测矩阵和失败分析。模型训练和 Agent 是两条线，我重点把两条线接成可复现的闭环。

## 6. 速记卡

### 6.1 核心公式

- Self-Attention：
  \[
  \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
  \]
- LoRA：
  \[
  W = W_0 + \frac{\alpha}{r}BA
  \]
- 注意力复杂度：\(O(n^2d)\)
- KV Cache 近似：\(2 \times L \times H_{kv} \times d_{head} \times n \times B \times \text{bytes}\)

### 6.2 项目数字

- 本地：Intel NUC i7-7000，无 CUDA，Ollama `qwen3.5:2b` Q8_0。
- 训练：2×A800 40GB，PyTorch 2.1 + CUDA 12.1 + Python 3.10。
- MVP 模型：Qwen2.5-Coder-7B-Instruct 级 7B。
- MVP 方法：bf16 LoRA，`r=32, alpha=64, dropout=0.05`。
- 数据：30–50 条种子 → 500–1000 条 MVP → 3k–10k 后续。
- 部署：merge adapter → GGUF Q4_K_M → Ollama。
- 评测：JSON 有效率、编译率、测试通过率、数值等价率、修复率、平均迭代数。

### 6.3 面试结尾话术

“这个项目最重要的不是宣称一个很大的模型，而是把数据验证、LoRA、GGUF 部署和带编译测试的 Agent 闭环串起来。当前 2B 基线已经能返回合法 JSON，但会漏头文件、破坏格式，这正好证明了为什么必须有编译和测试反馈。后续我会用 7B LoRA 和 Agent 修复对比，量化每一步的增量，并明确方言、数值容差和形式化验证的边界。”
